## OVERVIEW

Mozio API has been designed using a RESTful architecture, that relies on predictable,
resource-oriented URLs, and HTTP response codes to indicate errors. It uses built-in HTTP
features, like HTTP authentication and HTTP verbs, supported by most HTTP clients.
JSON is returned by all API responses, including errors. You will need to make sure the
appropriate _Content-Type_ is present in your HTTP requests (i.e _application/json_ ).
**Heads up:**
For the sake of simplicity, in all sample requests/responses we will omit the Content-Type
header since we will always use data in JSON format.
To start **developing** and **testing** , you can point your requests to https://api-testing.mozio.com.
When you are ready to move to **production** , use https://api.mozio.com.
Regardless of the environment, note that **HTTPS is required**. Any request not using HTTPS will
be ignored.
Also note that our current **API version** is 2, and all endpoints described in this document will
begin with /v2/.

#### AUTHENTICATION

For all of the resources in our API, you will also be **required** to have a valid **Mozio API key**.
You need to send it as a header, called _API-KEY_. If the API key is required and is not provided, the
API will return a HTTP 403 response.
**EXAMPLE: sending API requests with Mozio API key
GET /v2/some_resource**
API-KEY: <myMozioAPIkey>
HTTP/1.1 200 OK
{
"response": "OK"
}


In case you don’t have API keys, please contact the Mozio team to get them for you.

#### LOCALIZATION^1

Our API supports localization to over 30 languages by adding an optional _LANG_ header. The
expected value must use the IETF format.
Some of the supported languages include:
● English (en-US, default value)
● Spanish (es-ES)
● French (fr-FR)
● German (de-DE)
● Portuguese (pt-BR)
Note that only human-readable texts will be localized, meaning that the URLs or the name of the
parameters or objects in responses won’t.
**EXAMPLE: sending API requests and expecting responses in another language
GET /v2/some_resource/**
API-KEY: <myMozioAPIkey>
LANG: es-ES
HTTP/1.1 200 OK
{
"response": "¡Bienvenido!"
}

#### PAYMENTS AND CREDIT CARD DATA

Note that **no raw credit card information** is collected by our API during booking, nor any other
process for that matter: credit card details are captured securely by the application and are
never sent to our servers; we only capture secure, random tokens to identify the transaction that
are generated by one of our payments processor’s client libraries.

#### ERROR HANDLING

For most of the API responses, errors will probably come in 2 major categories: authentication
errors (HTTP 403), most likely due to missing or invalid API key, and bad requests errors (HTTP
400) due to malformed inputs.
For bad requests, the JSON object returned will include all fields that were malformed during the
request. For each of them you will receive a list of a 3-tuple structure containing a **code** (to
categorize the error), a **message** (targeted at developers) and **user_message** (targeted at
end-users, which can be null).
When the errors are not related to a specific param but to all data instead, most likely due to
global validation issues, a list of the same 3-tuple structure will be available inside a special
object called **non_field_errors**.
If you ever encounter an error that you cannot debug yourself and need assistance, please
contact the Mozio Tech team and include this error structure as part of your debugging request.

## INTEGRATION FLOW


In general terms, the integration flow can be summarized as a 3-step process:

1. Searching
2. Booking
3. Cancellation

#### SEARCHING

Searching refers to the process of giving some basic inputs describing the intended trip –the
start and end locations (e.g. JFK Airport to The Waldorf Astoria Hotel), the desired pickup time
(e.g. April 15th, 3:30 PM) and the number of passengers, and receiving back quotes that fulfil
that trip.
In case you don’t know the desired pickup time, our API can also calculate an estimated pickup
time using flight data (time, if domestic or international, and airline / flight number). For


domestic flight, we will calculate the pickup time for a transfer from the airport by adding 30
minutes to the flight datetime. If it’s international flight, we will add 60 minutes.
Since our API has to compose a list of quotes (using our in-house ground providers platform),
and also query our network of external providers’ APIs for quotes in real-time, not all quotes can
be returned immediately –it’s a dynamic process that inherently adds some delay. Therefore, the
search process is composed by 2 subprocesses: **search request** and **search polling**.
Search request, as the name implies, refers to the process of letting the API know to begin a
new search process.
Search polling is about the process of asking the API, every few seconds, about the results of
that search. Each time you poll for search results, new quotes are returned (the list of quotes is
dynamic –i.e. **poll results are not accumulable** ). You can poll until no more search results are
expected back.
At then end, each quote will have all data describing the offered trip, in general: the provider
fulfilling the service, the type of vehicle to expect, any restrictions that may apply (maximum
number of passengers and luggage allowed, schedules, boarding points, etc.), and total price for
all passengers.

#### BOOKING

After you have a list of quotes and your user chooses one of them, booking refers to the process
of requesting our external provider to secure and fulfil that trip described by the quote from
search results.
Additionally to data from the quote, you will be required to pass all contact details from the
passengers: names, email addresses, phone number and flight data (if relevant). Passengers
are also able to send special instructions to providers, if supported by them (e.g. “Please
announce yourself in the lobby” or “Please text me, my doorbell is broken”).
Similar to searches, the booking process is divided in **booking request** and **booking polling**. As
before, the idea is to first place the request for a reservation, and then, start polling while our API
connects to the provider’s API and receives a response.
After a reservation is placed successfully, our API will return a **confirmation number** that can be
used for any further API requests, and any Customer Support as needed by the passenger.
Contact details from the provider will be included as well. The passenger himself will receive a
confirmation email with details about the reservation and what to do next to meet the driver or
board the vehicle.


#### CANCELLATION

This process allows passengers to cancel an existing reservation and receive a full refund.
However, not all reservations are cancellable: all quotes have a **cancellation policy** describing
whether the trip is cancellable or not, and how many hours of notice are given to be entitled to a
100% refund.
Our API requires the confirmation number of the reservation to proceed with a cancellation.
Keep in mind that this operation cannot be undone and that refunds may take up to 5 business
days to be issued by our payments processor.
After a successful cancellation is made, the passenger will receive an email notification
confirming the operation.

## SEARCHING

#### STARTING THE PROCESS

**Endpoint** : /v2/search/
**Allowed methods** : POST
**Highlights:**
● You can choose to either send the locations’ addresses or gps coordinates. For an
airport, send the airports’ IATA code (e.g. JFK), and for other types of locations please
try to provide as much data as you can. Mozio’s API uses Google Maps API, so you can
also send the place_id from a given Google Maps API location.
● Please provide the pickup_datetime when possible. If you cannot and your search is
to or from an airport, you may use flight_datetime and our API will calculate an
estimated pickup time for it. By default we consider the flight as international you can
send flight_type as domestic otherwise:
○ For Airport pickups we add 30 minutes buffer for domestic and 1 hour for
international flights
○ For Airport drop-offs we add 2 hours 30 minutes buffer for domestic and 3 hours
30 minutes for international flights
● If you don’t provide either pickup_datetime or flight_datetime , the pickup time
will be set to 5 minutes from now.


● If you need to perform a round-trip search ( mode = round_trip ), don’t forget to provide
either return_flight_datetime or return_pickup_datetime
● To differentiate searches from different sources on your platform, you can pass us the
campaign and branch parameters. Campaign is meant to identify major different
sources of traffic, like “confirmation_email” or “cross-sell-email”, while branch is meant
to help differentiate things within the campaign itself such as different email creative.
Keep in mind that it is okay to send a campaign but no branch, but sending a branch
without a campaign is not allowed.
● **Important:** Our API allows 100 search requests per minute in the production
environment, after that the requests will be throttled. If you expect to have higher
volume, please reach out and we can increase the limit. In the testing environment , our
API allows 30 search requests per minute;
● **Important:** Mozio searches are valid for 20 minutes. If you try to book after that time, we
cannot guarantee that the pricing and availability will remain the same, and your booking
attempt may fail (search_expired error). To prevent this, please perform a new search to
obtain the most up-to-date results.

#### POLLING FOR RESULTS

**Endpoint** : /v2/search/<search_id>/poll/
**Allowed methods** : GET
**Highlights** :
● We recommend calling this endpoint approximately every 1-2 seconds for 10 seconds,
although the vast majority of our search results will be available in 3-6 seconds. There is
no point of polling for results every hundred milliseconds, as there will not be new results


```
in such a small timeframe. It is the same for doing a poll request right after the search
request, no results will be returned and everyone will just waste resources;
● You should keep polling as long as the more_coming value is true. However, always set
a timeout in your application to stop polling after a certain maximum amount of time, as
in rare cases errors can cause the API to never return false. Normally, the maximum
number of polls expected is 10.
● Every time you poll, results will contain different data. This is because our external
providers’ APIs return data at a different pace. This also implies that polling results are
not accumulable. We recommend returning these results to your customers as they
appear and not waiting for everything to finish.
● Important: Our API allows 30 poll requests for every search_id per minute,, after that the
request will be throttled. Our testing environment allows 10 poll requests for every
search_id, per minute.
● In the poll response, you'll find detailed information about the products offered by
different providers. Each product is identified by a result_id. Certain providers require
information about all passengers for whom a transfer is being booked. For instance, if
the number of passengers is 2, you'll need to provide additional passenger information
(extra_pax_info) when making a reservation. Failure to provide this information will result
in a 400 error code, accompanied by the following message:
{"non_field_errors":[{"message":"Missing required argument
extra_pax_info","code":"extra_pax_info_required","user_message":"Missing required
argument extra_pax_info"}]}
● You can filter the results by amenities by passing the selected amenity as a parameter to
this endpoint, e.g. if you want to receive in the response results from providers that have
enabled ride-tracking , you’ll do it the following way:
https://api.mozio.com/v2/search/8c0973af9d944917b05bd6bf1bcdc6a2/poll?amenities=ride_tr
```

### CANCELLATION POLICIES IN SEARCH RESULTS

During the search process, each result includes detailed cancellation policies to help users
understand the conditions for cancelling a trip. The cancellation information is returned in the
polling results under each result's main step.
The cancellation data is located in the cancellation dictionary under the policy key. This
information includes:
● Notice: The number of hours before the ride can be canceled.


● Refund Percent: The percentage of the refund that the passenger will receive if the ride
is canceled (always 100%).
The JSONPath for accessing this information is:
$.results[*].steps[?(@.main = true)].details.cancellation.policy
For example:
{
"cancellation": {
"amendable": true,
"cancellable_offline": true,
"cancellable_online": true,
"policy": [
{
"notice": 24,
"refund_percent": 100
}
]
}
}
This cancellation data is essential to display to users at the search stage to ensure they are
aware of the terms before booking.

#### STARTING THE PROCESS

**Endpoint** : /v2/reservations/
**Allowed methods** : POST
**Highlights** :
● As mentioned before, to create a reservation you will need both the search_id and
result_id from the selected quote from the search process. Apart from that, most of
the data required are contact details of the passenger(s).
● The response from this endpoint will inform you about the status of the reservation you
just tried to place; in most cases a successful response will be pending , meaning our


```
API is contacting the external provider and waiting for a response. After this, you will
need to start polling.
● The response from this endpoint should be checked, i.e. it cannot be assumed that each
time the response will be successful, sometimes the response will not be pending and
that means that a reservation hasn’t been successfully created
● Flight data (airline’s IATA code and flight number) is always required for a booking going
to/from an airport, unless you are trying to book an express train or a public bus, in
which case the search result will indicate flight data is not required. Specifically, you
must provide the airline's IATA code - it cannot be any other identifier of the airline, but
the IATA code ( e.g. “airline” = “LX” ) and the flight number (e.g. “flight_number” = “9202”.
If you don’t provide flight details, we will return an error “ invalid ”, “ Sorry, that airline is not
in our database. Contact via chat and we'll try to help ”
● If you reservation is for a round-trip trip ( mode = round_trip when searching), don’t
forget to provide return_airline and return_flight_number
● No credit card data was needed because the integrating application is in charge of
managing payment data
● If you select a transfer option that requires extra passenger information
( extra_pax_required = True ), please ensure to include this information in the reservation
payload. If you don’t do so, you won’t be able to create a reservation and will receive a
400 error instead. Below is an example of such a payload for your reference.
● Our API validates phone numbers using Google’s libphonenumber library , which follows
official national numbering plans.
```
### ● Important : Please send a reservation identifier from your side on the partner_tracking_id

parameter in the payload for this endpoint, it will facilitate the reconciliation of bookings
with finance teams.
**Duplicate reservation safety mechanism:**

1. **Same partner_tracking_id**
    If multiple /v2/reservations requests are sent using the **same partner_tracking_id** , only
the first reservation will be created. Subsequent requests with the same ID will be
rejected as duplicates.
2. **Same search_id**
    If a reservation is created using a search_id that has already been used for another
reservation, it will be flagged as a duplicate.
3. **Matching Passenger & Trip Details**
    If a new reservation request contains the exact same values for **all** of the following
fields as an existing reservation:
○ first_name
○ last_name


○ airline
○ flight_number
○ start_address
○ end_address
○ departure_datetime
○ number_of_passengers
⚠ **Tip:** To avoid duplicates, always generate unique partner_tracking_id values for each new

## RESERVATION CHANGES

To make changes to a reservation, first we need to do a re-search passing the reservation id
and the parameters we want to change, like a new start or end location, a pickup datetime etc.
After this re-search is done, using the search_id and result_id a new reservation will be created
using the reservation changes endpoint, passing again the old reservation id, this endpoint will
return a new reservation, with new reservation id. The old reservation will be cancelled. That’s


why only cancelable reservations can be changed. On a change, the price is subject to change
and you should be sure to charge/refund your customer as needed.
The change process is meant to be a much simpler than doing a full search and booking
because you only need to pass the information you want to change from an existing reservation,
and the search will only return options from the same provider the original reservation was
made with, making the search process much faster than a new search.

#### sms_notifications

sms_notifications is an internal amenity that is available for **all rides** , regardless of
whether the transportation provider explicitly offers it.
● **Price:** 1.99 USD (applied only if selected)
● **Availability:** Always available
● **Behavior:**
○ If this amenity is selected **and** the provider offers either:
■ ride_tracking , or
■ provider_driver_information
(these amenities will appear in the provider’s amenities list),
○ the customer will receive an SMS notification when the driver has been assigned.
If neither ride_tracking nor provider_driver_information is available for
the selected provider, the SMS notification will not be sent even if
sms_notifications is selected.

### ERROR CODES

##### GENERAL

**ServerError**
error_code = "server_error"
_It’s raised when the server encounters an unexpected condition_

##### AUTHORIZATION

**MissingApiKey**
error_code = "required_api_key"
_It’s raised when the user doesn’t provide an API key in the request_
**InvalidApiKeyException**
error_code = "invalid_api_key"
_It’s raised when the user provides a wrong API key_

##### RESERVATION CANCELLATION

**AlreadyCancelledException**
error_code = “res_already_canceled”
_It’s raised when a user sends a request to cancel a reservation that is already canceled_
**TooLateToCancelException**
error_code = "too_late_to_cancel"
_It’s raised when a user sends a request to cancel a reservation that is not cancellable, i.e. cancellation
policy doesn’t allow the cancellation_


**CancellationErrorException**
error_code = "server_error"
_It’s raised when there was an error in the reservation cancellation, it’s returned from the provider side_

##### RESERVATION CREATION

**DuplicateReservation**
error_code = "duplicate_reservation"
_It’s raised when there is a request to create a reservation that we consider a duplicate reservation. A
duplicate reservation is a reservation that matches any of following criteria:_
**_Reservation Status_** _: If the reservation is in a 'PENDING' or 'COMPLETED' state, it's considered a
duplicate._
**_Partner Tracking ID_** _: If there's a partner tracking ID and it hasn't been set to ignore partner tracking
duplicate checks, and there exists a reservation with the same partner tracking ID that hasn't been
canceled, it's considered a duplicate._
**_Reservation Details_** _: If there's a reservation with matching details like the first name, last name, airline,
flight number, start and end locations, departure datetime, and number of passengers, it's considered a
duplicate._
**TripPriceChanged**
error_code = "trip_price_changed"
_It’s raised when the price has changed between doing a search a making a reservation request_

##### SEARCH

**SearchResultNotFound**
error_code = "search_result_not_found"
_It’s raised when the result_id passed in the reservation create request can’t be found._
**SearchExpired**
error_code = "search_expired"
_It’s raised when the search has expired. We cache results for 20 minutes, after that time you need to
refresh the search_
**429 Too Many Requests**
status_code = 429


_It’s raised when a user has sent too many requests in a given amount of time (we have limits for search
request and search poll requests: the limit is 100 search request and 30 search poll requests per
search_id per minute_
**400 Bad request**
error_code = “too_far_apart”
_It’s raised when doing a search request (or performing a search on Mozio website/white labels) and the
distance between the from and to locations exceeds 500 miles._
